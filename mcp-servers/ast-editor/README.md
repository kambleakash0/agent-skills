# AST Code Editor MCP Server

A robust, language-agnostic Model Context Protocol (MCP) server that provides AI coding agents with the ability to edit files surgically via Abstract Syntax Trees (AST) instead of relying on token-heavy, brittle search-and-replace or diff operations.

## Why AST Edits?

Every non-AST edit format — search/replace, unified diff, whole-file rewrite — requires the model to copy text *perfectly* from a file it saw once. One whitespace mismatch on a 4,000-line file and the edit fails. AST edits sidestep the problem entirely: the model names the target (e.g., `LRUCache.get`) and provides the new code; the parser figures out where it lives.

Geometric AGI benchmarked every major format across 4 models and 29 edit tasks. **AST edits were the only format to hit 100% correctness on 3 of 4 models, with 18x fewer output tokens than whole-file rewrite, and zero format failures.** Full methodology and results: [AST Edits: The Code Editing Format Nobody Uses](https://geometricagi.github.io/2026/04/02/ast-edits.html).

## Estimated Token Savings

Per-edit output token savings versus other common edit formats:

| Edit size | File size | vs whole-file rewrite | vs unified diff | vs search/replace |
| :--- | :--- | :--- | :--- | :--- |
| 1-line tweak | 100 LoC | 3–5x | ~1.5x | ~1.5x |
| Function body rewrite | 500 LoC | 8–12x | 2–3x | 2–3x |
| Function body rewrite | 4,000 LoC | **15–20x** | 3–5x | 3–5x |
| Add 2 lines to a function | any size | **~20x** (via `insert_in_body(at="top")` / `insert_in_body(at="bottom")`) | 5–10x | 3–5x |

Per-read input token savings versus reading the entire file:

| Read task | File size | AST reader tool | vs full file read |
| :--- | :--- | :--- | :--- |
| One function's source | 500 LoC | `read_symbol` | **~20x fewer tokens** |
| One function's source | 2,000 LoC | `read_symbol` | **~50-100x fewer tokens** |
| Class API (10 methods, no bodies) | 500 LoC | `read_symbol(depth="interface")` | **~10x fewer tokens** |
| Import block only | any size | `read_imports` | **~20-50x fewer tokens** |
| Structural overview (names + line numbers) | any size | `list_symbols` | **~15-30x fewer tokens** |
| One function's signature | any size | `read_symbol(depth="signature")` | **~50-200x fewer tokens** |

**For daily agent users, a realistic 40-60% reduction in total tokens per session is achievable, on average** (combining output savings from surgical edits with input savings from targeted reads).

The savings come from four compounding effects:

- **Output tokens:** Using `insert_in_body` (`at="top"` / `at="bottom"`, or anchored with `after=` / `before=`) for small additions instead of rewriting whole function bodies
- **Input tokens:** Using `read_symbol` (`depth="full"` / `"interface"`) / `read_imports` to read only what's needed instead of entire files (~10-20x fewer input tokens per read)
- **Discovery:** `list_symbols` / `read_symbol(depth="signature")` instead of reading whole files
- **Zero format failures:** AST edits never fail on whitespace drift, eliminating retry loops that plague other formats.

**Cross-cutting features:**

- **Decorated functions and classes** (Python and JS/TS `@decorator`, Java annotations): decorators are part of the symbol. They are preserved on body edits; `read_symbol`, `replace_function` and `delete_symbol` include them; a leading comment belongs above the first of them (`edit_leading_comment` puts it there and finds an existing one there), and `insert_sibling(position="before")` goes above them and that comment, so the comment stays on the symbol it documents. This holds for TypeScript methods too, whose decorators the grammar places beside the method in the class body, for decorated Python classes, for a C++ template's `template <...>` header and for a Ruby Sorbet `sig`. `replace_signature` keeps them as written unless the new signature includes its own, which then replace them.
- **Layout-aware `add_method` / `add_field`**: the new member is indented like the class's existing members (falling back to the file's indent unit, then the language default: 4 spaces for Python and Java, a tab for Go, 2 spaces otherwise), keeping the content's relative indentation; in a class indented with tabs that indentation is written in tabs too (one per indentation step of the content), so a snippet written with spaces fits a tab-indented file. The lines that start inside a multi-line string literal of the content (a triple-quoted string, template literal, heredoc, raw string, C string continued with `\`) or a Ruby embedded document (`=begin` ... `=end`, at column 0) keep their text, here and in every tool that re-indents content (`replace_function`, `replace_function_body`, `insert_in_body(at=...)`, `insert_sibling`, `edit_leading_comment`); a Python docstring, a Ruby `<<~` heredoc and a Java text block, whose indentation the language strips, move with the code instead, every line by the same amount. A method follows the last member after one blank line, or none when the class's methods have no blank lines between them (a C++ member template counts as a method; TS interface members stay one per line) or the last member is a C++ access label (`public:`), and one-line content after stacked one-line members (fields) is stacked with them. In a C++ class whose last method is followed by an access label (`public:`, `protected:`, `private:`), the new method goes right after that method, spaced as methods are, so it gets the same access; a comment after that method on its line stays with it, a method inside an `#if`/`#ifdef` block (either branch) counts as the last method (the new one goes after the `#endif`), and a label moved off a method's line is indented like the class's other labels, or at the class's indentation. A C++ class with no label after its last method, or with no methods, gets the new method after its last member. Content in `read_symbol`'s shape copied from another class (its first line without indentation, the later lines at the indentation they had there) is indented as a whole, a Python def without decorators only when it was read at the indentation of this class's members. A field goes before the first member (after a Python class docstring, and below the access label a C++ class body opens with, so it gets that section's access), with a blank line after it when that member is a method (a C++ member template counts), and a comment after the `{` on its line (`class K { // NOLINT`) stays there. In a Java enum both go after the constants, and a `;` is added after them when they have none. No blank line is added before the closing brace, and a braced body on one line (`class K {}`, `class K { a() {} }`, Go `struct{ A int }`) is opened up over several lines, its existing members on a line of their own. A Python or Ruby class written on one line (`class K: pass`) is refused. Both tools look only at containers, so a name a struct or interface shares with a function (`struct stat` and `int stat(...)`) is the struct, a typedef of a struct declared apart (`typedef struct Node Node;`) is that struct, and a function target is refused (use `insert_in_body`).
- **Layout-aware `add_key`**: in JSON objects, Python dicts, JS/TS object literals, YAML flow mappings and TOML inline tables the new entry follows the container's layout (one key per line at the existing indentation, inline objects stay inline, a trailing comma is kept, and a comment on the last entry's line stays there); an empty JS/TS or YAML `{}` becomes `{ key: value }` (TOML: `{ key = value }`). A YAML key with no value gets a nested block mapping one indentation level deeper (inside a flow mapping, an inline `parent: { key: value }`). YAML and TOML keys are quoted only when they need it: `my key` and `a.b` stay plain in YAML, while `a:b`, `yes`, `123` or a leading `-`/`#`/`&` get quotes (in the quote style most of the file uses); in TOML anything but a bare key (letters, digits, `_`, `-`) is quoted, and dots separate the parts of a dotted key, so `b.c` adds `c` under `b` and a name with a dot in it must be passed quoted (`'"example.com"'`). A JSON or YAML key passed already in quotes is used as given. A key the container already has is refused with a pointer to `replace_value`, for every format, naming a target that works (quoted where the key has a dot, inside flow mappings and inline tables too).
- **Layout-aware `append_to_array`**: JSON arrays, TOML arrays, YAML flow sequences and Python lists keep their layout: an inline array stays inline (`[1, 2]` becomes `[1, 2, 3]`, `[]` becomes `[3]`), an array with one element per line gets a new line at the elements' indentation (also one aligned under its `[` whose `]` closes the last line), a trailing comma is kept (the new element gets one too), and comments are not elements: one on the last element's line stays there, after the comma (`2,  # two`), and a value that ends with a comment gets its comma before it (`3,  # new`). A Python list whose `[` and `]` are on lines of their own with nothing between them gets the value on a line of its own, with a comma. A YAML block sequence gets a new `- value` item.
- **Config paths from the top level**: a dotted config target is followed from the top of the file, one key per segment: `a.b` is key `b` under the top-level key `a`, never an `a.b` nested deeper (such as `x.a.b`), and in TOML a plain `version` is a top-level key, not one inside a `[table]` (use `project.version`). One path syntax covers JSON, YAML and TOML and every config tool (`read_symbol`, `replace_value`, `add_key`'s `parent_target`, `delete_key`, `append_to_array`, `remove_from_array` and `edit_leading_comment`): a segment in double quotes is one key taken literally, dots included, its escapes resolved as in a JSON string (`"editor.fontSize"`, `a."b.c".d`), and in TOML single quotes work too (`a.'b.c'`), as in a TOML dotted key, whose syntax TOML paths share. Keys compare by the names they spell, so `"a.b"` finds `a.b: 1`, `'a.b': 1` and `"a.b": 1` in YAML, and `[x.'y.z']` and `[ x . "y.z" ]` are both TOML table `x."y.z"`. Keys inside YAML flow mappings and TOML inline tables are part of the path. Elements of arrays are not addressable by path (`a.0` is a key named `0`).
- **Byte-correct slicing**: multi-byte characters (emoji, `═`, `→`) handled safely in source text.
- **Import placement**: `add_import` skips exact duplicates. A new import goes into the group it belongs with, a group being a run of imports, includes or requires with no blank line or other code between them (comments may be; a conditional of includes counts as one include, a CommonJS `require` as an import). The group is picked by language. Python: a group holding imports of the same top-level package, else the standard-library group for a standard-library module and the group of other modules for others, relative imports with relative imports. C/C++: `<...>` with `<...>`, `"..."` with `"..."`, never a group of only the file's own header (`"foo.h"` in `foo.cpp`). Go: standard-library paths (no dot in the first path element) with standard-library paths, others with others, never with cgo's `import "C"`. JS/TS: relative paths (`./`, `../`) with relative paths, packages with packages, a `require` with requires. Java: static with static. Ruby: `require_relative` with `require_relative`. When several groups fit, the one with an import sharing the longest leading path with the new one wins (package parts, directories: `from app.y import z` goes with `from app import x`, `#include <sys/types.h>` with `<sys/stat.h>`), else the first; when none fits, the import goes after the file's last import. In a group that is already sorted it goes at its sorted place, else after the group's last import. Python sorts as isort and ruff do: module names without case, numbers in numeric order, `import x` lines before `from x import` lines in a group that orders them that way, else both together. The other languages sort by the path or module text (C/C++ includes as written, with their brackets or quotes). The import goes above the next import and the comment lines right above it, but below a comment above the group's first import, which heads the group; a comment that applies to the next line stays on its import even when the new import sorts first (`@ts-ignore`, `@ts-expect-error`, eslint or tslint `disable-next-line`, pylint `disable-next`, `biome-ignore`, `deno-lint-ignore`, `prettier-ignore`, `NOLINTNEXTLINE`, Flow suppressions, istanbul, c8 or v8 `ignore next`, Go `//nolint` and `//lint:ignore`, `noinspection`). The blank lines between groups stay as they are. Python `from __future__` imports stay first: a new one goes after the existing ones, or before the file's first import, and other imports go after them; a `from __future__` import that its group would place after code goes right after the module docstring, before any other statement, with a blank line on each side. Go: inside an `import ( ... )` block the same rules apply to the block's blank-line groups of specs, an alias sorting by its path (`"io"` goes between `"fmt"` and `"os"`); a block written on one line (`import ("fmt"; "os")`, `import ()`) takes the spec inline at its sorted place; without a block, a spec given without its keyword (`"fmt"`, `f "path/filepath"`) is written as `import "fmt"`; and nothing goes between `import "C"` and its cgo preamble comment (the new import goes after `import "C"`). A file's first import goes after its preamble (a package clause, `#!` and encoding or magic comments, the module docstring, `'use strict'` and other directives, TS `///` lines, `#pragma once`, an include guard's `#define`, and a header comment set off by a blank line), with a blank line above it and one below it (two before a Python def or class).
- **Doc-comment-aware deletion**: `delete_symbol` by default removes the contiguous leading comment block above the symbol (Godoc, Javadoc, `#`/`//` comment runs) so docs don't become orphaned. Opt out with `include_leading_comments=False`. The block ends at a blank line and at a comment line indented deeper than the symbol, which belongs to the code above it (`    # end of f` under f's last line, a commented-out YAML list item), for this and every tool that finds a leading comment: `insert_sibling(position="before")` goes below such a comment, and `edit_leading_comment` neither removes nor replaces it. Such comment lines right below a symbol's last line belong to it: `delete_symbol` removes them with it and `insert_sibling(position="after")` goes below them (`read_symbol` and `replace_function` leave them out). A Ruby `=begin` ... `=end` document directly above a symbol is its leading comment. Only real comments count, for this and every other tool that finds a leading comment: a line that starts with `#` or `//` inside a multi-line string, template literal or YAML block scalar is text. A `#!` line and the encoding or magic comments after it (`# -*- coding: utf-8 -*-`, `# frozen_string_literal: true`) at the top of a Python or Ruby file are never taken for a symbol's comment, by this or any other tool.
- **Layout-aware deletion**: the blank lines that separated a deleted symbol go with it, so the rest keeps the file's spacing: deleting the first symbol of a file or class body leaves no blank lines at the top or after the `{`, deleting the last one leaves none before the closing brace (and the next top-level symbol keeps its own separation, such as Python's two blank lines), and between the two symbols that remain only the wider of the two gaps stays. Only empty lines and lines of spaces and tabs are blank: a form feed line (a Python page break) next to the symbol stays. A symbol that shares a line with other code (`class A { a() {} b() {} }`, `x = 1; y = 2`) is cut out of that line instead, with the `;` or `,` that ends it (the last entry of a one-line literal takes the one before it: `{ a: 1, b: 2 }` minus `b` is `{ a: 1 }`) and a comment after it at the end of the line; the spaces that were before it stay between the code on both sides. `replace_function` likewise replaces only such a symbol's own text, and refuses content that ends with a `#` or `//` comment when code follows the symbol on its line.
- **Syntax-checked saves**: before anything is written, the edited file is re-parsed with its tree-sitter grammar. An edit that would introduce a syntax error into a file that parsed cleanly is refused with the error's line and column (e.g. `Edit refused: the result would have a syntax error at line 11, column 2 (missing '}')`), and the file is left unchanged. Files that already had syntax errors are not guarded, so you can keep working on them. For `.py` files Python's own parser (that of the interpreter running the server) decides: it catches the indentation errors tree-sitter lets through and accepts newer syntax the grammar does not know (PEP 696 type parameter defaults). For `.json` files the `json` module overrules the grammar wherever it would reject valid JSON, and comments in JSONC files stay allowed; exponents written with a `+` (`1e+2`), which tree-sitter-json cannot parse, are masked before parsing, so files that use them are checked like any other. Other languages have no second parser, so valid code using syntax the grammar does not support (very new language features, macro-heavy C/C++) can be refused: if you are sure the code is valid, make that edit with your normal edit tool.
- **Line endings and byte order marks preserved**: CRLF files stay CRLF and LF files stay LF, whichever tool makes the edit, and blank lines at the end of a file are kept as they were (deleting the last symbol does not leave extra ones behind); a file whose last line has no line break keeps it that way. A UTF-8 byte order mark stays at the start of the file, whatever the edit adds or removes at the top; it never shows up in tool output, and content that starts the file with one leaves a single mark. Files that are not UTF-8 (UTF-16, UTF-32, Latin-1), also UTF-16 or UTF-32 without a byte order mark and files with NUL bytes, are refused with a message saying so, and left unchanged. Write content, snippets and anchors with `\n` line breaks: inserted text is converted to the file's style, and a `\n` in a snippet or anchor matches a CRLF line break. Content is split into lines on `\n` (or CRLF) only, so a form feed, vertical tab, U+0085, U+2028 or U+2029 inside a string literal or comment stays where it was written. Only spaces and tabs count as indentation, so when content is re-indented a form feed at the start of a line (a Python page break, `\fdef g():`) or a U+2028 starting a line inside a string stays, and a form feed before the target's own `def` is not copied onto the new lines. In a file that mixes CRLF and LF, every line the edit does not rewrite keeps its own ending (the lines next to the edit too, though they read like lines it removed or added); a line it writes takes the ending of the lines it replaces when they agree, else of the lines on both sides when they agree, else the file's most common one.
- **Body snippets and anchors** (`replace_in_body`, `delete_in_body`, `insert_in_body(after=…, before=…)`): a snippet matches its exact text (`\n` matching CRLF) where it neither starts nor ends inside a token of code, an identifier, number, keyword or operator: `x = 1` is not found in `max = 10`, nor `= 1` in `a == 1`, `el` in `$el` or `foo` in Ruby `foo?`; inside a comment or string (not in an interpolation's code) it may start or end between any two words, and it may end at a Python backslash continuation. Without an exact match, its lines match whole lines of the body with one indentation added to or taken from each of them, so a block copied at column 0 or deeper than in the file is found: blank lines match blank lines, spaces and tabs at line ends do not count, tabs and spaces differ, and a snippet that starts or ends in the middle of a line must match exactly. The text of a multi-line string is never shifted: a line that starts inside one is matched only as written in the file (Python docstrings, Ruby `<<~` heredocs and Java text blocks, which move with the code, aside). An exact match wins, except that when every exact match is inside a string or comment, shifted matches in other places count too. The match must be unique: two or more places are refused with their line numbers (`Snippet matches 2 places in body of 'f' (lines 2, 4)`), and text found only inside longer tokens is refused saying so. A deletion that leaves its lines without code takes the whole lines, indentation and line break included; a comment after the deleted code on its last line stays, at the line's indentation; a Python body is never left without a statement (replace the snippet with `pass`). New text goes in indented as the snippet matched: moved with a shifted match's lines; after an exact one-line snippet that left out its line's indentation (or starts mid-line), its later lines given that indentation unless they are that deep already; after an exact snippet of several lines, or when already at the file's indentation there, as written; in Python, when one reading of the indentation does not parse and the other does, the other is taken. `insert_in_body` puts new text on lines of its own when the anchor ends its line (`after`) or starts it (`before`), indented like the anchor (new text at column 0 beside an anchor written with its indentation goes at the anchor's, and text in `read_symbol`'s shape goes in as written), and inside the block that an `after` anchor's line opens (`if (x) {`, `if x:`); in the middle of a line, or where the new line would start in the text of a string or heredoc (not a docstring, `<<~` heredoc or Java text block, whose lines are indented like code), it is placed byte for byte. Lines of new text that go into a string of the file keep their text.
- **Tab-indented code**: every tool that writes source content over several lines (`replace_function`, `replace_function_body`, `replace_in_body`, `insert_in_body`, `insert_sibling`, `add_top_level`, `add_method`, `add_field`) writes the content's indentation steps in tabs where the file indents with tabs there: the place's indentation has a tab, or, at column 0, most of the indented lines of the code it replaces or goes beside start with one (the text of its strings and lines aligned under a bracket aside), or, with no such lines, the file is Go or mostly tab-indented. Each step of the content's own indentation becomes one tab; the text of multi-line strings, Ruby `=begin` documents, and the spaces that align a block comment's lines or a line continued inside a `(` or `[` stay as written. Config files are never converted.

### Language-specific design decisions

A few tools have language-specific semantics where multiple reasonable interpretations exist. The chosen behavior is documented here for transparency:

**`add_field` (Ruby and Go) — option (a): literal text passthrough**

- **Ruby:** `add_field("LRUCache", "  attr_accessor :capacity")` inserts the literal string at the top of the class body. The tool does **not** auto-wrap bare names in `attr_accessor` — you provide the exact text you want (whether that's `attr_accessor`, `attr_reader`, `@instance_var = nil` in `initialize`, or `CLASS_CONST = 42`).
- **Go:** `add_field("Cache", "\tversion int")` inserts the literal string inside the `struct { ... }` body. The tool does **not** infer types from bare names — you provide the full Go field declaration.
- **Rationale:** consistent with how `add_field` works for other languages (Python, JS/TS, C++) where the caller provides the full source text. The alternative option (b) — auto-wrapping (e.g. `attr_accessor :foo` from the name `foo`) — would be more magical but harder to use for edge cases (typed fields, readonly fields, field with default value, etc.).

**`add_method` (Go) — option (a): top-level sibling insertion**

- `add_method("Cache", "func (c *Cache) Has(key string) bool { ... }")` locates the `type Cache struct { ... }` declaration and inserts the new method **immediately after it, at the top level** (not inside the struct's braces), indented with tabs and with a blank line on each side.
- **Rationale:** Go methods are lexically top-level, not nested inside their receiver type — this matches how Go code is actually written. The alternative option (b) — refusing because "Go methods aren't inside structs" — would be pedantically correct but force callers to use `insert_sibling("Cache", content, position="after")` instead, which loses the semantic signal that this is a method addition.

Sorted means plain, case-sensitive order (a single name always is), or else isort's and ruff's order by type: CONSTANT_CASE, then CamelCase, then the rest, each without case (`from typing import TYPE_CHECKING, Any, cast` plus `Dict` gives `TYPE_CHECKING, Any, Dict, cast`); names that fit both use plain order (`Any, Dict` plus `TYPE_CHECKING` gives `Any, Dict, TYPE_CHECKING`). A name sorts by the name it imports (`b as bb` as `b`, a TS `type B` as `B`). The list keeps its layout: names written one per line in parentheses or braces get the new one on a line of its own at their indentation (aligned under the `(` or `{` when they are), above the next name and the comment lines right above it, or at the end after the last name's line and its comment, with the trailing-comma style kept (`from x import (alpha, gamma)` one per line plus `beta` gives `alpha`, `beta`, `gamma`, one per line); a comment heading the list stays first, and a next-line directive (see Import placement above) stays on the name below it. Inline lists, and a Python list without parentheses, stay inline, the new name going before the next one (`from x import a, c` plus `b` gives `a, b, c`; `import { a, c } from "m"` plus `b` gives `{ a, b, c }`). For a default or namespace import (`import Foo from ...`, `import * as ns from ...`) use `add_import` with the full line. |
| `remove_import_name` | `file_path`, `module`, `name` | Remove one name from a multi-name named-import statement (Python and JS/TS). If the last named import is removed and no default/namespace binding remains, the whole line is removed; removing the last name beside a default binding (`import D, { a } from "m"`) is refused, as it would leave empty braces: use `remove_import`, then `add_import` the default binding. In parentheses or braces, a name on a line of its own goes with that line and the comment at its end, comments on other lines stay, and a last name without a comma takes the comma before it. |

### Comments & docstrings

| Tool | Parameters | Description |
| :--- | :--- | :--- |
| `edit_leading_comment` | `file_path`, `target`, `op`, `comment=""` | Edit the contiguous leading-comment block above a named symbol, which is above its decorators/annotations, a JS/TS `export` and a C++ `template <...>` header; a symbol that other code comes before on its line has none of its own and is refused. `op="add"` inserts (refused if the symbol already has a leading comment; the error quotes it, so a following `op="replace"` can repeat lines worth keeping, such as `// eslint-disable-next-line` or `//go:noinline` directives); `op="replace"` replaces (or inserts if none); `op="remove"` deletes. `comment` includes its markers, is re-indented to the symbol, and is required for `add` and `replace` (ignored for `remove`). Works for `#` / `//` / `/* ... */` / Javadoc `/** ... */` and a Ruby `=begin` document (alone or with `#` lines beside it, kept at column 0); a Ruby Sorbet `sig` and a TS function's overload signatures are part of the symbol, so the comment goes above them; a comment line indented deeper than the symbol ends the code above, so `op="add"` puts the new comment between the two; a `/* ... */` that follows code on its line (`int x = 1; /* n */`) is not taken as a leading comment. In YAML and TOML the target is a key path (a YAML key with no value too) or a TOML `[table]` by its header's names (`tool.uv`); a key that does not start its line (inside a flow mapping or inline table) is refused, since the comment line above would belong to another key. |
| `replace_docstring` | `file_path`, `target`, `new_docstring` | Replace or insert a Python function/class docstring, or the module's for `target=""`. Python-only. `new_docstring` must be one Python string literal with its quotes, for every target: bare text, an f-string, a bytes literal or an empty new_docstring is refused (the error says to write it with its quotes, as in `'"""Summary."""'`) and the file is left unchanged. Inserting one into a body on its signature's line (`def f(): return 1`) is refused: rewrite the body with `replace_function_body`. A new module docstring goes before the first statement (a `from __future__` import stays after it), right below a `#!` line and an encoding comment, and below a header comment set off by a blank line, which keeps its blank lines; a comment right above the first statement stays with it, below the docstring. One blank line follows the docstring (two before a def or class), and in a file with no statement it goes last. An f-string or bytes literal at the top of the module is no docstring and stays. |

### Dict/list editing (JSON, YAML, TOML, Python module-level dict/list literals, AND JS/TS object literals)

Values (`content`, `value`) are literal source text in the file's own syntax (`'"2.0.0"'`, `42`): quote strings where the format requires it.

| Tool | Parameters | Description |
| :--- | :--- | :--- |
| `replace_value` | `file_path`, `target`, `content` | Replace the value of an existing key. Targets as for `delete_key`: JSON/YAML/TOML dotted path from the top level (`"editor.fontSize"` for a key with dots; keys inside YAML flow mappings and TOML inline tables too, which stay inline); Python `DictName.keyExpr`; JS/TS `VarName.key` (a shorthand `{ key }` becomes `key: <content>`). A YAML key with no value (`a:`) gets one (`a: 3`, or a nested block below the key for content of several lines or a block sequence or mapping; a first line that is only `\|`, `>-`, an `&anchor` or a `!tag` stays after the colon). In source files it also replaces the value of a variable, constant or field (Python `X = 1` and class attributes, JS/TS `const X = 1;`, each name of `let a = 1, b = 2` alone, and class fields `A.x`, Go `var`/`const`, C/C++ globals, C++ fields and static members, macros, Java fields, Ruby constants and locals, a heredoc's body too): only the value (`int x(1);` and `int y{1};` keep their delimiters), and a declaration without one gets one (`let x;` becomes `let x = 2;`, `X: int` becomes `X: int = 2`, `int g;` becomes `int g = 2;`). Refused: a function, class or type (rewrite it with `replace_function`), a name that shares one value with others (`a = b = 1`, Go `var c, d = f()`), and one that cannot have a value of its own (`extern`, TS `declare`, an abstract field, Go `var e, g int`; for C struct fields and Go constants see the language table). |
| `add_key` | `file_path`, `parent_target`, `key`, `value` | Add a key-value pair to a dict/object/mapping/table. For config, `parent_target` is a dotted path from the top level (use `""` for root; a TOML `[table]` by its header's names, `a."b.c"` for `[a.'b.c']`); YAML flow mappings (nested ones too) and keys with no value and TOML inline tables work too. For JSON and YAML `key` is one name, dots included. For Python it is the dict variable name; for JS/TS the name of a module-level `const`/`let`/`var` (or `export const`) object literal, `as const` / `satisfies` included. Both may continue into nested literals (`CONFIG."db"`, `CONFIG.server`). JSON keys are quoted for you, YAML and TOML keys only when they need it (in TOML, dots make a dotted key), JS/TS keys only when they are not valid identifiers, Python keys are key expressions (`'"timeout"'`). The entry follows the container's layout (one per line, inline, trailing comma), and a key that already exists is refused (use `replace_value`). |
| `delete_key` | `file_path`, `target` | Delete a key-value pair. Targets: JSON/YAML/TOML dotted path from the top level (`"editor.fontSize"` for a key with dots; keys inside YAML flow mappings and TOML inline tables too, cut like JSON entries with their comma); Python `DictName.keyExpr`; JS/TS `VarName.keyName` on `const`/`let`/`var` or `export const` object literals (handles regular pairs, `{ key }` shorthand, methods, and quoted `"complex-key"`). Python and JS/TS paths may continue into nested literals (`CONFIG.server.port`). For JSON, Python and JS/TS, the adjacent comma is also removed (an entry on its own line goes with that whole line, including its same-line comment), and deleting the only entry leaves `{}`; other YAML and TOML keys go with their lines. For an entry of an inline object literal passed as a function argument (`foo({ x })`), use `delete_in_body` on the enclosing function. |
| `append_to_array` | `file_path`, `target`, `value` | Append a literal value to a list/array/sequence. For Python, `target` is the list variable name; for config, a dotted path from the top level. The array keeps its layout: inline stays inline (`[1, 2, 3]`), one element per line gets a new line at the elements' indentation, and a trailing comma is kept; comments are not elements, and the new element's comma goes before a comment (see Layout-aware `append_to_array` above). |
| `remove_from_array` | `file_path`, `target`, `value_match` | Remove the first matching element from a list/array/sequence. `value_match` is compared with each element's source text after stripping whitespace. Comments are not elements: one on its own line goes with that line and the comment at its end, comments on other lines stay (one above it, or after the element before it, too), the trailing-comma style is kept (a last element with no comma after it takes the comma before it), and removing the only element leaves `[]` (a YAML block sequence becomes `key: []`, before a comment on the key's line). |

### Navigation & reading (read-only)

| Tool | Parameters | Description |
| :--- | :--- | :--- |
| `list_symbols` | `file_path` | Formatted outline of all top-level functions, classes, methods and data with line numbers, one `<kind> <name> (line N)` per symbol, the name being its target (a symbol's line is that of its first decorator, `export`, Ruby Sorbet `sig` or first overload signature). JS/TS exported declarations are listed under their own names, an anonymous default export as `default`; generators and functions bound to a `const`/`let`/`var` as `function`, other `const` names as `constant`, `let`/`var` names as `variable` and class fields as `field`, TS abstract classes as `class` (with their abstract methods), and TS enums, type aliases, interfaces and namespaces as `enum`, `type`, `interface` and `namespace`. Nested classes are listed under their containers with their members (`class A.B`, `method A.B.m`), as are Python module variables and class attributes, Ruby constants and locals, C/C++ fields, macros, typedefs, globals, destructors and operators, Java fields and Go type aliases and variables (see the language table). Of a name a scope declares more than once, the target is listed, once. In C, C++, Java, JS and TS every entry is listed under the target that finds it at the listed line: overloads with their parameter types (`method A.m(int) (line 2)`), a C++ or Java method beside a field of its name as `A.x()` (in JS/TS the method is `A.x` and the field is not listed), a C++ definition outside its class by its qualified name (`function A::f`), and a tag or type that shares its name with another symbol after its keyword, so the line reads `struct struct stat (line 1)` or `type type User (line 2)`; an entry no target reaches is left out. In Python and Ruby a name defined again is listed again, and the name targets the first. Names that a pattern binds (`a, b = 1, 2`, `const {a} = o`) are not listed, and a declaration of several names (`int a, *b;`) lists each. Go lists types with their methods, then the names of `var` and `const` declarations, then functions. |
| `find_references` | `file_path`, `target` | Syntactic search for all occurrences of an identifier (no scope awareness, so same-named unrelated identifiers show up too), matched per identifier rather than as a dotted path, returned as `line N: <source line>` in file order, by line and column. |
| `read_symbol` | `file_path`, `target`, `depth="full"` | Return source text of a single named symbol. `depth` controls how much: `"full"` returns the entire source (typically **10-20x fewer tokens** than the whole file), from its first byte, so the later lines keep their file indentation: exactly what `replace_function` and `delete_symbol` take (with a Go `type`/`var`/`const`, a closure's key, a TS `declare`, the C typedef or declaration around a struct, a Ruby `private`, a TS abstract method's `;`), ready to be edited and given back to `replace_function` as is; `"interface"` returns a class stub (header + fields + method sigs with `...`, each member at its indentation relative to the class header and ending as written, with its `;` or `,`; a C/C++ class closes with `};`) or a function's signature; `"signature"` returns signature-only (a method with no body, such as a TS abstract or Java interface method or a C++ `A() = default;`, is its whole declaration, and a Go struct its header, `type A struct`). Both start where the full text starts, except that a function's or class's signature leaves out its decorators and a JS/TS `export` (`handler: () =>`, `RunE: func() error`, `declare function f(a: number): void`, `extern "C" int f(int a)`, `private def m(x)`, `typedef struct N`, or `typedef struct` without a tag), and a closure's interface is its signature. A TS overload group and a Python `@overload` group give the implementation's signature, a Ruby endless method its part before the `=`. For a Go type, `"interface"` is its declaration as `"full"` reads it plus its methods' signatures (`type N int` has no signature, but its interface lists its methods). Both refuse a variable, constant, field, type alias, macro or C/C++ forward declaration, saying what it is (`'X' is a constant, which has no signature ...; read it with depth='full'`). A declaration of several names (`int a, *b;`, Java `int x, y;`) reads whole for each of them, and a comment after the symbol on its last line is no part of it. For a config key path, `"full"` (the only depth config files take) returns the key's value (an empty string for a YAML key with no value). |
| `read_imports` | `file_path` | Return all import/include statements in the file. |

**Target format:** Use the exact function name (e.g., `get`) or dotted `Class.method` path (e.g., `LRUCache.get`). In C, C++ and Java an overload takes its parameter types (`A.m(int, String)`, `A.m()`, C `f(void)` being `f()`), a C++ definition outside its class its qualified name (`A::f`), and a name that a field shares with methods targets the field (the method is `A.x()`). A C/C++ tag or TS type alias or interface that shares its name with another symbol takes its keyword (`struct stat`, `union u`, `class C`, `type User`, `interface Props`), in front of a dotted path (`type N.User`). JS/TS exported declarations are targeted by their own names (`export function add` is `add`); an anonymous `export default function/class` is `default` (and its methods `default.run`), and `const f = () => {...}` is `f`. Decorated functions are fully supported — decorators are preserved when replacing bodies or signatures, and included when deleting or replacing the full function.

**Tip:** Call `list_symbols` first to discover exact target names before editing. This avoids guessing and makes subsequent edits much more reliable.

## Which tool should I use?

A decision guide grouped by intent. Start at the top and pick the narrowest match.

### Discovering what's in a file (do this first)

- **Don't know what symbols exist?** → `list_symbols`
- **Need one specific function's full source?** → `read_symbol` (`depth="full"`, the default — 10-20x cheaper than reading the whole file)
- **Need a class's public API (methods + fields, no bodies)?** → `read_symbol(target, depth="interface")`
- **Need just a function's signature?** → `read_symbol(target, depth="signature")`
- **Need to see a file's imports/dependencies?** → `read_imports`
- **Where is a symbol used?** → `find_references`

Dotted targets descend into closures: Go `stdioCmd.RunE` (func_literal in struct field), TS `app.handler` (arrow function in object literal).

### Adding new content

| Intent | Tool |
| :--- | :--- |
| New top-level function, class, constant, or type alias | `add_top_level` (use `position="top"` to prepend after preamble) |
| New method in an existing class | `add_method` |
| New field/attribute/member in a class | `add_field` |
| New content before or after a top-level symbol | `insert_sibling(position="before" \| "after")` (`"before"` goes above the symbol's leading comment) |
| New lines at the top of an existing function body | `insert_in_body(at="top")` |
| New lines at the bottom of an existing function body | `insert_in_body(at="bottom")` |
| **New lines at a specific spot inside a function body (anchored to existing text)** | `insert_in_body(after=…)` or `insert_in_body(before=…)` |
| New parameter on an existing function | `add_parameter` |
| New import or `#include` | `add_import` |
| New name in an existing `from X import …` or `import { a, b } from "mod"` | `add_import_name` |
| New comment above a symbol | `edit_leading_comment(op="add")` |
| New Python docstring on a function/class | `replace_docstring` |
| New key in a dict/object/mapping/table (any lang) | `add_key` |
| New item in a list/array/sequence (any lang) | `append_to_array` |

### Modifying existing content

| Intent | Tool |
| :--- | :--- |
| Rewrite the full function (signature + body) | `replace_function` |
| Rewrite only the body, keep the signature | `replace_function_body` |
| **Change one statement/block inside a large body** | `replace_in_body` (scoped snippet match) |
| Change only the signature, keep the body | `replace_signature` |
| Change only the leading comment above a symbol | `edit_leading_comment(op="replace")` |
| Change only the Python docstring | `replace_docstring` |
| Change the value of an existing key (config, Python dict, JS/TS object) | `replace_value` |

### Removing content

| Intent | Tool |
| :--- | :--- |
| Remove a function, method, or class | `delete_symbol` (consumes leading doc comment by default) |
| **Remove one statement/line inside a function body** (a route mount, a middleware call, a key of an inline object-literal argument) | `delete_in_body` |
| Remove a parameter from a function | `remove_parameter` |
| Remove an import or `#include` | `remove_import` |
| Remove one name from a multi-name named-import (Python or JS/TS) | `remove_import_name` |
| Remove a leading comment above a symbol | `edit_leading_comment(op="remove")` |
| Remove a key from a dict / config / JS-TS object literal | `delete_key` |
| Remove an item from a list/array | `remove_from_array` |

### Anti-patterns to avoid

- **Don't use `replace_function` or `replace_function_body` to change a few lines** — use `replace_in_body` (scoped snippet match) or `insert_in_body(at="top" \| "bottom")` for appending/prepending. Rewriting the whole function is wasteful and error-prone.
- **Don't use `replace_signature` to add or remove one parameter** — use `add_parameter`/`remove_parameter`.
- **Don't use `replace_value` to add a new key** — use `add_key`. `replace_value` only updates existing keys, and `add_key` refuses a key that already exists.
- **Don't use `add_import` to add a name to an existing `from X import …` or named import** — use `add_import_name`.
- **Don't guess at target names.** Call `list_symbols` first. Names are case-sensitive and must match exactly.

### Escape hatches

- **Deleting several related symbols?** Call `delete_symbol` once per target. There is no `delete_group` tool: the extra calls cost less than a grouped primitive would.
- **Editing a sub-expression inside a method chain** (dropping `.references(...)` from `integer("x").notNull().references(...)`)? Use `replace_in_body` with the literal snippet when it is unique; for arbitrary expression surgery use your normal edit tool, since ast-editor does no pattern matching on expression trees.
- **Rewriting a whole file whose structure changes substantially?** Use your normal write tool.
- **Valid code refused by the syntax check** (very new language features, macro-heavy C/C++)? Make that edit with your normal edit tool.

## Prerequisites

This MCP server uses [`uv`](https://docs.astral.sh/uv/) to manage its Python environment and dependencies automatically. Install `uv` if you don't have it already:

**macOS / Linux:**

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

**Windows (PowerShell):**

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

**Homebrew (macOS):**

```bash
brew install uv
```

**pip (any platform):**

```bash
pip install uv
```

Verify the installation:

```bash
uv --version
```

> For more options (Docker, Cargo, WinGet, etc.), see the [official uv installation docs](https://docs.astral.sh/uv/getting-started/installation/).

**uv 0.9.17 or newer is required.** This server's `pyproject.toml` sets a 7-day dependency cooldown (`[tool.uv] exclude-newer = "7 days"`). Older uv versions can't parse that relative duration. They print a warning and ignore the setting. A plain `uv sync` or `uv run`, including the `uv --directory … run` launch commands below, then discards the committed `uv.lock`, re-resolves to the newest compatible versions (even ones published in the last 7 days), and rewrites the file. Upgrade with `uv self update`, `brew upgrade uv`, or `pip install -U uv`, depending on how you installed it. Upgrading doesn't undo an earlier rewrite: restore the original `uv.lock` with `git checkout HEAD -- uv.lock` in this folder, or copy it again from the archive you downloaded.

The server depends on `mcp`, `tree-sitter`, and a tree-sitter grammar package for each supported language. `uv` handles all of these automatically on first run.

## Logging & Debugging

The server logs all tool invocations and errors to **stderr** (safe for stdio transport — does not interfere with JSON-RPC). Logs include timestamps and severity levels.

To inspect logs when running under Claude Desktop, check:

- **macOS:** `~/Library/Logs/Claude/mcp*.log`
- **Windows:** `%APPDATA%\Claude\logs\mcp*.log`

For interactive testing, use the [MCP Inspector](https://modelcontextprotocol.io/docs/tools/inspector), which provides a UI for exercising each tool with custom parameters and inspecting responses.
